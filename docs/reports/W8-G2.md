# W8-G2: the grass fill's worst frames

All figures are **CPU-side, headless (null renderer), this laptop, nothing else running** (`tasklist` showed no other Godot
process before every timed run; what else Windows was doing is UNVERIFIED). Stdout and stderr were written to separate files.
No game, editor or window was launched. The machine's own speed drifted during the day: `terrain_cpu_ms` (untouched code,
the same 234 chunks every run) read 1.8 s in the first idle batch and 2.8-4.3 s later, so each figure below names its state.

## What the measurements said (before any fix)
- **The lead's numbers reproduce only with another process running.** My first three runs overlapped another session's test
  suite (seen in `tasklist` afterwards): mean 3.3-3.6 ms, worst 13.6 / 23.2 / 13.8 ms, terrain 3.6 s. Idle, the same code:
  **mean 1.63-1.67, p95 2.8-2.9, worst 4.14 / 4.56 / 4.24 ms** (fast state), 1.69-1.75 / 3.1-3.3 / 4.6-4.7 (slow state).
- **The lead's structural explanation is right, and it is the floor.** The new `worst_unit` counter named the dearest unit
  in every run: the **grass layer of one cell, 4.0-4.7 ms** (240 candidates) against a 1 ms budget checked only between
  units. So every run has a frame over 4 ms whatever the budget, and under contention that one unit stretches 3-5x: the
  13-23 ms frames are the structural unit times the machine, both theories at once.
- **Phases** (`--probe-phases`, two runs, summed over the sprint; the clock reads add ~20 %): prepare 141-145 ms (17 %),
  candidate draw + grid slope/height 206-223 (24 %), land multipliers incl. the keep-out filter 118-130 (14 %), zone
  sampling 63-71 (8 %), exact slope 19-21 (2 %), **transform + exact height + colour maths 274-301 (33 %)**, upload
  (`set_instance_transform/color/custom_data`) 23-25 (3 %). The upload is 3 % **because the null renderer discards it**; what
  it costs with the real renderer is UNVERIFIED and not measurable here, so the `buffer`-at-once variant was not pursued.
  Nothing dominates enough to be the fix; the fix had to be scheduling.
- **Thinning was a second hidden cost:** `_last_thin` was reset on every working frame, so the whole-lattice re-thin
  (109 cells x 7 layers) ran 480 times a sprint, 301 ms, worst 1.4 ms, outside the fill timer.
- **Spawn fill** (plain `--probe`, slow state): mean 2.34, **p95 6.2, worst 11.1 ms** (one grass unit), 44 frames over 4 ms.

## What changed (scheduling and cost only; density, palettes, zones, blade shapes, layer data untouched)
- `GrassLayer.fill` is now `begin()` + resumable `step(max_candidates)`; the RNG is drawn in one fixed order so any split
  places the same blades. `Grass.fill_step_candidates = 32` (0 = a whole layer); a cell's `prepare` is its own unit.
- A completed layer is thinned on the spot (`_thin_layer`); the full pass runs only when the player has moved 2 m (84x a sprint).
- `first_fill_budget_ms = 2.0` until the lattice first settles after `rebuild()` (the spawn is a load, not play).
- Counters: p95 from a 0.1 ms histogram, frames over 4/8/16 ms, steps, worst unit and its layer, prepare and thin time.
  Probe: `PROBE cost` carries them, `PROBE sprint` adds `max_unfilled_50m` and `settle_frames`, `PROBE grass_settled` is the
  settled lattice at the sprint's start, and the probe now waits for the grass to settle before printing (`settle_frames`).
- The step default is in `grass.gd`; `vale.tscn`, `cell_size` and the radius are unchanged.

## Results, idle, 10 sprint runs at step 32 (fast and slow states mixed)
| | before (idle) | after |
|---|---|---|
| fill mean ms / working frame | 1.63-1.75 | **1.16-1.23** |
| p95 | 2.8-3.3 | **1.5-1.8** |
| worst | 4.1-4.7 (every run > 4) | **2.1, 2.2, 2.2, 2.4, 2.4, 2.6, 2.7, 2.9, 4.8, 7.4** |
| frames over 4 / 8 / 16 ms | 1-7 / 0 / 0 | **0 / 0 / 0 in 8 runs; 1 / 0 / 0 and 2 / 0 / 0** |
| max_unfilled_30m / 50m | 0 / - | **0 / 0 in every run** |
| spawn: mean / p95 / worst | 2.34 / 6.2 / 11.1 | **2.39 / 3.2 / 4.7**, settled at tick 270 (was 315-319; 139-321 across runs) |

**Targets:** p95 <= 3 ms met in every run; `max_unfilled_30m = 0` kept (and 50 m); worst <= 6 ms met in 9 of 10. The 7.4 ms
(and a 4.8) were **one 32-candidate step stretched 5-12x**, and a suite's child run once held a 36.5 ms frame: the OS taking
the thread mid-step. No step size shortens that; what the change did is remove the 4.5 ms floor it multiplied. The worst
frame is therefore not asserted; the test bounds p95 (<= 6), over-4 (<= 5 %) and over-8 (<= 3) so it cannot flap.
**Trade-off, chosen for the ground:** at an honest 1 ms a working frame does less than the old 1.65 ms overrun did, so the
tail of the far ring (3-5 cells, 50-70 m out, thinned to a quarter and inside the shader fade) is still pending when the
sprint ends; `max_unfilled_50m = 0` says none of it was ever within sight. test_grass_sprint's `pending <= 1` became `<= 8`.
